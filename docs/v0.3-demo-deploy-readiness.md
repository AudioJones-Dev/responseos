# v0.3 Demo Deploy — Readiness Plan

**Status:** Planning artifact. **Nothing in here is executed.** This documents the path to a
shareable, password-gated demo URL so the decision can be made with the full picture.

**Authorization gate:** A production deploy is **v0.3 work and is not yet authorized**
(ROADMAP "Hard constraints": *no production deploys until v0.3 readiness gates clear*).
This plan does not lift that gate — it defines what clearing it looks like.

---

## 1. Goal

A URL a teammate can send to a prospect that shows the polished ResponseOS UI running on
**seeded mock data**, behind a simple access gate. Not a multi-tenant production system — a
controlled demo of the operator console + client portal + marketing surfaces.

What the demo does **not** need (and must not claim to have): live Twilio/Retell/Vapi/Stripe
integrations, real customer data, HIPAA posture, or real authentication. The mock-first data
layer (ADR-0001) already renders every page without a database or secrets, so the product is
demoable today on a laptop. This plan is only about hosting it at a shareable URL.

## 2. Current state (what's already true)

- **UI rebuild** (PR #43, pending review) makes every surface dark-first and presentable.
- **Auth substrate** (PRs #39/#40/#41) is in: schema columns, session derivation, and a root
  `proxy.ts` running Clerk middleware that **passes through when `CLERK_SECRET_KEY` is absent**.
- **Mock-first** data layer: `lib/auth/session.ts` falls back to an `aj_admin` placeholder
  session when `RESPONSEOS_DEV_SESSION` is unset and Clerk env is absent, so pages render
  against seeded data with zero secrets.
- Build prerenders all routes; `npm run build` + `npm run start` serves the whole app locally.

## 3. The blocker to resolve first — `proxy.ts` collision

There are **two competing root `proxy.ts` designs**:

| Source | `proxy.ts` does | Status |
|---|---|---|
| **PR #41 (merged/landing)** | Clerk `clerkMiddleware`; enforces sign-in when `CLERK_SECRET_KEY` set, else pass-through | current on master |
| **PR #14 (May 8, stale)** | HTTP basic-auth gate via `BASIC_AUTH_USER`/`BASIC_AUTH_PASS`; allowlists `/api/health` | conflicts with #41; also predates the Account/Appointment renames |

**PR #14 cannot be merged as-is** — it overwrites the Clerk proxy and is built on pre-rename
code. Its *idea* (an edge access gate + uniform session behind it) is still the right shape for
a demo, but it must be re-expressed on top of the current `proxy.ts`, not as a replacement.

**Recommended reconciliation:** fold a basic-auth check **into** the existing Clerk `proxy.ts`
as a thin pre-step that runs only when `BASIC_AUTH_USER`/`BASIC_AUTH_PASS` are set (and Clerk
env is absent). One small, reversible function; keeps the kill-switch property (unset the two
vars → gate disappears, no redeploy). Salvage the runbook from PR #14; close PR #14 itself.

## 4. Two viable demo shapes — pick one

### Option A — Basic-auth gate + uniform `aj_admin` session (recommended for speed)
- Viewer enters one shared username/password at the edge; behind it every page renders as the
  seeded `aj_admin` operator against seeded data. No Clerk project, no per-user accounts.
- **Pros:** fastest to stand up; no identity-provider setup; trivially reversible kill switch.
- **Cons:** everyone sees the same session; not a real auth demo.
- **Fits:** "show prospects the product and the numbers."

### Option B — Real Clerk + seeded users
- Provision a Clerk project, set `CLERK_SECRET_KEY` / publishable key / webhook secret, map
  seeded users via the 32C webhook, exercise real sign-in and tenant isolation.
- **Pros:** demonstrates real auth + tenant scoping; closer to production.
- **Cons:** materially more setup (Clerk project, webhook routing to the deployed URL, seeded
  user↔org mapping); more secrets to manage.
- **Fits:** "show that auth + multi-tenant isolation actually work." Better as a later milestone.

> Recommendation: ship **Option A** for the prospect demo now; keep Option B for when the demo
> graduates toward a pilot.

## 5. Readiness checklist (Option A)

Infra & data
- [ ] **Hosting:** Vercel project importing this repo (framework auto-detected: Next.js 16).
- [ ] **Database:** managed Postgres 16 (Neon recommended). One database, seeded — not customer data.
- [ ] Run `prisma migrate deploy` then `prisma db seed` against the Neon database.
- [ ] Confirm `next build` succeeds in Vercel with `DATABASE_URL` / `DIRECT_URL` set.

Access gate
- [ ] Implement the basic-auth pre-step in `proxy.ts` (§3 reconciliation), behind env vars.
- [ ] Allowlist `/api/health` for uptime checks.
- [ ] Verify kill switch: unsetting the two vars disables the gate with no redeploy.

Smoke checklist (against the Vercel URL)
- [ ] Gate prompts for credentials; wrong creds → 401; correct creds → app.
- [ ] `/`, `/pricing`, `/demo`, `/industries/*` render (public marketing).
- [ ] `/client/dashboard` shows the recovered-revenue hero on seeded data.
- [ ] `/admin` + `/admin/leads` render the console + Lead Events table.
- [ ] `/api/health` returns ok without the gate.
- [ ] No console errors; dark theme intact.

Rollback
- [ ] Documented: unset gate vars (instant), or redeploy previous Vercel build, or pause project.

## 6. What the human must provide (no secrets in the repo)

These are **operator inputs**, supplied directly in the Vercel/Neon dashboards — never committed:

1. **Vercel account** + permission to import the repo.
2. **Neon (or other Postgres 16) account**; it yields `DATABASE_URL` / `DIRECT_URL`.
3. **Demo gate credentials**: choose `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` values.
4. (Option B only) **Clerk** project keys + webhook secret + seeded user/org mapping.

`.env.example` stays placeholders-only; real values live in Vercel/Neon env settings.

## 7. Constraints this plan respects

- No live provider integrations (Twilio/Retell/Vapi/Stripe/etc.) — mock adapters stay in force.
- No real secrets committed; `.env.example` placeholders only.
- Not represented as HIPAA-compliant anywhere in the demo.
- Tenant isolation unchanged; the demo runs on seeded data, not real customers.
- This remains **v0.3** and requires explicit authorization before any deploy step runs.
