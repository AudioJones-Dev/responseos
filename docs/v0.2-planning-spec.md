# ResponseOS v0.2 Planning Spec

## Purpose

v0.2 moves ResponseOS from a mock-data internal foundation into a database-backed, client-portal-ready, integration-ready product. v0.1 ships an internal AJ Digital operator console and a read-only client dashboard backed entirely by static fixtures. v0.2 swaps the mock layer for real Postgres-backed persistence, adds authentication and tenant-aware access, expands the data model toward the canonical event-ledger architecture, and stands up the client portal for real read traffic. Live provider integrations remain behind mock/service adapters until explicitly authorized in v0.3.

## Strategic Direction

ResponseOS remains:

- AI Revenue Recovery Platform.
- Not an AI receptionist clone.
- Not a QuoteIQ clone.
- A system for capturing missed demand, qualifying leads, booking opportunities, and proving recovered revenue.

The OFFER + RECOVER frameworks remain the product's organizing principles. v0.2 strengthens the data and access foundations that make the RECOVER stages (Respond / Evaluate / Capture / Offer / Verify / Escalate / Report) measurable and auditable.

## OpenClaw Decision

OpenClaw is optional and sandboxed. OpenClaw should **not** be the primary live phone-answering engine. OpenClaw may be used later as:

- Workflow / agent gateway.
- Internal automation assistant.
- Multi-channel routing layer.
- Scheduled follow-up worker.
- Owner / staff notification assistant.

The primary live voice layer remains:

- Twilio.
- Retell.
- Vapi.
- Bland.
- Or an equivalent dedicated telephony / voice-agent provider.

**Reason.** Real-time inbound phone answering requires hardened telephony, streaming audio, transcription, barge-in, routing, compliance controls, webhook reliability, and call observability. Those properties are productized in dedicated voice runtimes today; OpenClaw's strengths sit in workflow orchestration and assistant patterns, not in carrier-grade phone answering. Treating OpenClaw as the primary voice runtime would re-create solved problems and introduce reliability + compliance risk on the most customer-visible surface of the product.

## Grok Voice Experimental Provider Candidate

- Grok Voice API may be evaluated as an experimental realtime voice-agent provider.
- Useful for low-cost voice pilots, website/app voice assistants, internal operator copilots, and sales qualification flows.
- Should remain behind the provider abstraction layer.
- Marked experimental until quality, reliability, pricing, concurrency, failure modes, and compliance posture are verified.
- Should NOT be used for HIPAA, legal, medical, or regulated workflows until compliance eligibility and contractual requirements are independently verified.

## v0.2 Core Goals

1. Replace mock data with Supabase / Postgres-backed persistence.
2. Add real authentication and tenant-aware access (Clerk-backed, with role enforcement).
3. Upgrade the organization model toward account / tenant architecture (rename `organizations` → `accounts`, introduce `workspaces` for sub-tenant grouping).
4. Add an event ledger for webhook and workflow idempotency.
5. Add real client portal read views backed by tenant-scoped queries.
6. Add provider connection records without storing raw secrets in the database (encrypted at rest, decrypted at request time, key material in Secrets Manager).
7. Add an audit-log foundation covering admin actions, prompt changes, break-glass entries, and data exports.
8. Add webhook event storage (raw body, signature header, signature_valid flag, dedupe hash).
9. Add a normalized conversations / SMS model so message threads survive across providers.
10. Add a basic billing / outcome-fee model so v0.3 can wire real Stripe + invoicing.
11. Prepare for white-label client branding (custom domain, theme variables, RBAC) without shipping the branding UI yet.
12. Keep live voice integrations behind mock / service adapters until explicitly authorized.

## Proposed v0.2 Data Model Expansion

Planning targets only — do not implement these models in code during this task. The list aligns with the v0.2 expansion documented in `docs/data-schema.md` and the canonical model in `docs/research-report.md`.

- `accounts` — tenant root (rename of `organizations`).
- `workspaces` — sub-tenant grouping below accounts.
- `provider_connections` — per-tenant credentials handle, encrypted at rest.
- `locations` — branches / service areas per account.
- `leads` — durable prospect / customer record.
- `conversations` — SMS thread root grouping inbound + outbound.
- `sms_messages` — per-message rows under a conversation.
- `call_segments` — turn-by-turn legs (speaker, sequence, text, confidence).
- `call_transcripts` — full transcript artifacts with PII redaction + retention policy.
- `webhook_events` — vendor HTTP callbacks with raw body + signature validation state.
- `events` — immutable event ledger; replay, audit, ROI recomputation.
- `workflow_runs` — n8n / internal workflow execution log.
- `qa_logs` — call QA scoring + review (rubric_version, findings_json).
- `audit_logs` — admin action stream, break-glass, exports.
- `quotes` — estimate header (replaces `quote_requests` in expanded form).
- `quote_items` — line items.
- `quote_versions` — revision history.
- `followups` — SMS / email / call reminders + drip sequences.
- `payments` — charges, deposits, refunds, BNPL.
- `billing_accounts` — AJ ↔ tenant billing relationship.
- `usage_meters` — platform usage for rebilling.
- `invoices` — AJ invoices to clients.
- `outcome_fees` — computed performance fees per period with evidence references.
- `roi_metrics` — replaces `revenue_metrics` with expanded KPI facts.
- `files` / `media` — uploaded artifacts (recordings, photos, exports) with R2/S3 keys + retention policy.
- `consent_records` — per-contact consent state (recording, AI handling, marketing) with jurisdiction + timestamp.

These tables are documented and discussed; none of them ship as TypeScript types or Prisma models in this task.

## v0.2 API Direction

- Authenticated admin routes — `aj_admin` and `operator` roles; cross-tenant read/write.
- Authenticated client portal routes — `client_admin` and `client_viewer` roles; tenant-scoped only.
- Tenant-scoped reads — every query derives `account_id` from the session, never from client input.
- Webhook idempotency — provider event IDs (Twilio `MessageSid`/`CallSid`, Retell `call_id`, Stripe `event.id`, GHL `event.id`) stored in the ledger before any business mutation.
- Canonical envelopes — `{ ok: true, data }` / `{ ok: false, error: { code, message, details? } }` (already enforced in v0.1 stubs and carried forward).
- Rate-limit plan — public REST 120 req/min/key; quote creation 20/min/tenant; appointment booking 10 concurrent holds/tenant; reports 30 req/min/user; webhooks dedupe + reject invalid signatures.
- Provider webhook signature validation before production — Twilio `X-Twilio-Signature`, Retell `x-retell-signature`, Stripe `Stripe-Signature`, HighLevel `X-GHL-Signature`, n8n shared secret.
- No live production webhooks until explicitly authorized — v0.2 wires the ingest path and ledger persistence; live provider routing waits for v0.3 authorization.

## v0.2 Security Direction

- Role-based access control — four roles (`aj_admin`, `operator`, `client_admin`, `client_viewer`) enforced at the route layer.
- Tenant isolation — `account_id` filter on every read and write; row-level enforcement where the database layer supports it.
- Audit logs — admin actions, prompt changes, break-glass entries, data exports.
- Webhook signature validation — staged behind a feature flag in v0.2; mandatory before any production traffic in v0.3.
- Idempotency keys — `Idempotency-Key` header on all POST mutations, 24-hour retention.
- Environment-secret separation — local `.env.local`, staging, production, and a future `prod-hipaa` overlay; AWS Secrets Manager (or equivalent) holds the canonical values.
- No hardcoded secrets — `.env.example` is placeholders only; the rule is enforced by the v0.1 audit and continues into v0.2.
- PHI / PII minimization — store only what's necessary for service, QA, and billing; per-tenant retention modes (full / PII-scrubbed / metadata-only).
- Recording / transcript access controls — raw artifacts and redacted review copies live in separate storage paths and policies; QA reviewers see redacted only.
- Provider BAA review before regulated verticals — vendor allowlist locked per compliance tier; med spas, legal, and medical require BAA chain in force before onboarding.

- Live Twilio / Retell / Vapi integration with signature verification and call/event persistence.
- Real Stripe billing — Payment Intents, hosted pages, webhook ingest.

## Future Knowledge Layer / Agent Grounding Layer

ResponseOS may later include a client-specific knowledge layer that stores and organizes approved business knowledge used to ground AI voice, SMS, booking, quote, and support workflows. This is a **roadmap target for v0.4 or later**, not part of v0.2 and not part of the current database/auth foundation.

Potential future knowledge sources:

- client FAQs
- service descriptions
- pricing rules
- service areas
- business hours
- escalation policies
- approved scripts
- objection handling
- quote rules
- warranty policies
- CRM notes
- call transcripts
- client SOPs
- uploaded documents
- product/service manuals
- internal implementation notes

### Roadmap placement

| Version | Theme |
|---|---|
| v0.2 | DB / auth / data-access foundation (this spec) |
| v0.3 | Retell / Twilio provider pilot + webhook event ledger |
| v0.4 | Client knowledge base + agent grounding layer |
| v0.5 | Billing / outcome-fee ledger |
| v1.0 | Client-ready Revenue Recovery OS |

### Why this is **not** v0.2

The knowledge layer should land only after tenant isolation, auth, audit logs, provider integrations, and retention policies are stronger. Implementing it inside v0.2 would distract from the data-access foundation v0.2 is meant to deliver, and would import knowledge-management surface area before the security gates in `security.md` are mature enough to host client-facing ingestion safely.

### Required gates before client-facing knowledge ingestion

Before any client-facing knowledge ingestion ships, ResponseOS must support:

- tenant isolation
- source ownership
- upload permissions
- audit logging
- retention policy
- transcript / recording controls
- PII minimization
- deletion / export workflow
- approved-source controls
- human review for sensitive knowledge
- regulated-workflow restrictions

### Out of scope for v0.2

Documenting this roadmap does **not** authorize any of the following inside v0.2:

- RAG implementation
- vector search
- embeddings indexes or pipelines
- file-upload surfaces
- Obsidian or other personal-knowledge integrations
- Codex automations
- new dependencies, provider SDKs, or secrets
- new database models
- production deployment

Future data model candidates are documented as planning only in `docs/data-schema.md`. Architectural placement is documented in `docs/architecture.md`. Product framing is documented in `docs/research-report.md`.
