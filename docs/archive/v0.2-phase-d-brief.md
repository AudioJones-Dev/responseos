## 1. Why Phase D exists

Phases A–C are merged. The data layer compiles, seeds deterministically, and is wired through every page + API route, but **nothing currently exercises a real Postgres connection**. The 53 unit tests run against mocked Prisma (`vi.mock`). That leaves three gaps the spec calls out:

1. No integration coverage of `lib/data/*` against a real database.
2. No CI job that proves the seed is byte-deterministic.
3. No CI job that proves `npm run build` succeeds against the seeded DB (only the no-DB fallback path runs today).

Phase D closes those three gaps and is the last v0.2 milestone before v0.3 (Auth.js + `Organization`→`Account` rename).

## 2. In scope

- Add a Postgres-backed integration test suite under `tests/integration/`.
- Add a `test:integration` npm script + a Vitest config (or include flag) that targets `tests/integration/**` exclusively.
- Add a `tests/factories/*.ts` directory of typed factories (deterministic ids `org_test_001`, `lead_test_001`, etc.) per spec §7.

  - Runs `npm run build` with `DATABASE_URL` pointed at the seeded service (the DB-backed build smoke called for in spec §10).

## 4. Concrete deliverables

### 4.1 `package.json` script

Add **one** line:

```json
"test:integration": "vitest run --config vitest.integration.config.ts"
```

Leave `test` as-is (unit only). The unit run must stay fast and DB-free.

### 4.2 `vitest.integration.config.ts` (new file)

Mirror `vitest.config.ts` but:

- `include: ["tests/integration/**/*.test.ts"]`
- `exclude: ["tests/unit/**", "tests/e2e/**", "node_modules/**"]`
- `test.hookTimeout: 30_000` (Postgres container + migration + seed need headroom)
- `test.testTimeout: 15_000`
- Same `@/` alias.
- Coverage block can stay; no need to gate on threshold yet.

### 4.3 `tests/factories/` (new dir)

One file per model that the integration suite exercises (start with the four v0.2 additions plus `Organization`, `User`, `Lead`, `Booking`):

- `makeOrganization(overrides?) → Prisma.OrganizationCreateInput`
- `makeUser({ role, organizationId }, overrides?)`
- `makeAssessmentReport({ organizationId, status }, overrides?)`
- `makeEngagement({ organizationId, assessmentReportId }, overrides?)`
- `makeAuditLog({ organizationId, actorUserId }, overrides?)`
- `makeWebhookEvent({ provider }, overrides?)`
- `makeLead({ organizationId }, overrides?)`
- `makeBooking({ organizationId, leadId }, overrides?)`

Each factory takes deterministic counter-based ids (`org_test_001`, `org_test_002`, …) so snapshot diffs are stable. Factories return create-input shapes; tests call `prisma.<model>.create(...)` themselves so failures point at a specific table, not at a helper.

### 4.4 `tests/integration/` suites

Minimum required files:

- `setup.ts` — exports `connectTestDb()` and `resetTestDb()`. `resetTestDb` truncates every table in dependency order (or runs `prisma migrate reset --force --skip-seed` then re-seeds). Called from a `beforeEach` in each suite.
- `data-tenant-matrix.integration.test.ts` — for **every** accessor in `lib/data/*` that takes `organizationId`, exercises the three-case matrix from spec §7:
  1. `aj_admin` reads across tenants → success.
  2. `client_admin` of org A reads org A → success.
  3. `client_admin` of org A reads org B → `code: "tenant_scope_denied"`.
- `data-accessors.integration.test.ts` — at least one positive-path test per public function in each `lib/data/*` module. Verify the exported accessors compose correctly against a real DB (joins, indexes, default ordering).
- `audit-log.integration.test.ts` — verifies that mutating accessors emit `AuditLog` rows with the documented shape.
- `seed-determinism.integration.test.ts` — runs `prisma migrate reset --force` + `prisma db seed` twice in sequence, then diffs every table's `findMany({ orderBy: { id: "asc" } })` snapshot. Asserts deep equality across both runs (acceptance criterion §10: "deterministic IDs matching the existing `lib/mock/*` fixtures").
- `mock-parity.integration.test.ts` — for each table seeded from a `lib/mock/*` fixture, assert the seeded rows match the mock fixtures field-for-field. Catches drift between seed and mock data (Q8 strict-fixture-parity decision in spec §11).

### 4.5 `.github/workflows/ci.yml` changes

Add a second job named `integration` alongside `validate`. Skeleton:

```yaml
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: responseos
          POSTGRES_PASSWORD: responseos
          POSTGRES_DB: responseos_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U responseos"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 10
    env:
      DATABASE_URL: postgresql://responseos:responseos@localhost:5432/responseos_test
      DIRECT_URL: postgresql://responseos:responseos@localhost:5432/responseos_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx prisma migrate deploy
      - run: npx prisma db seed
      - run: npm run test:integration
      - run: npm run build
```

Notes for the implementer:

- Postgres **16** to match the version Neon/Supabase will most likely run when Q1 is revisited in v0.3. Don't pin to 15.
- `DATABASE_URL` and `DIRECT_URL` are identical because the GH Actions service container is unpooled — that is intentional and matches the spec's connection-pooling note in §8.
- The build step at the end is the spec §10 DB-backed-build acceptance check. If it fails, the job fails — do not paper over it.
- Keep `concurrency: ci-${{ github.ref }}` so a re-pushed branch cancels the old run.

## 6. Acceptance criteria for Phase D

Phase D is done when:

- [ ] `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` are all still green from the unchanged `validate` job.
- [ ] `npm run test:integration` exists and passes locally against a Postgres 16 container.
- [ ] CI's new `integration` job is green on the PR.
- [ ] Every `lib/data/*` accessor that takes `organizationId` has the three-case tenant matrix executed against a real DB.
- [ ] Seed-determinism test asserts identical row sets across two consecutive seed runs.
- [ ] Mock-parity test asserts seeded data matches `lib/mock/*` fixtures field-for-field.
- [ ] Spec §10 acceptance items "`npm run build` succeeds with `DATABASE_URL` set to the seeded local Postgres" is wired into CI.
- [ ] No new runtime deps in `package.json`. No changes to `prisma/`, `lib/`, `app/`.
- [ ] PR is opened **draft** until CI green, then mark-ready for user merge — same flow as PRs #5 / #6 / #7.

## 7. Open implementation questions (non-blocking — defaults given)

1. **Reset strategy between integration tests** — `prisma migrate reset --force --skip-seed` per `beforeAll` of each file is slow. Default: truncate every table inside `resetTestDb()` per `beforeEach`, only run `migrate reset` once per process in `globalSetup`. Codex may adjust if a faster pattern is obvious.
2. **Coverage thresholds** — none enforced in Phase D. Spec §7 targets 80% on `lib/{auth,data,db,validation}/**` but says nothing about gating CI on it. Default: keep the lcov reporter, do not fail the build on threshold misses; revisit in v0.3.
3. **Parallelism** — Vitest defaults to file-level parallelism. With one shared Postgres service container, parallel writes will race. Default: set `test.fileParallelism: false` and `test.poolOptions.threads.singleThread: true` in `vitest.integration.config.ts`. If integration suite runtime grows past ~60s, switch to per-test schema isolation later.
4. **Migration drift check** — Should CI run `prisma migrate diff --exit-code` to catch schema/migration desync? Default: yes, add it as a step in the `integration` job before `migrate deploy`. One extra line, high signal.
