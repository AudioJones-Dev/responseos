## 1. Goals + non-goals

### Goals (in scope for v0.2)

- Stand up real Postgres persistence behind the existing 11 v0.1 models with **fallback to mock fixtures** when `DATABASE_URL` is unset, so `npm run build` and `npm run dev` keep working without a database.
- Add four new tables to support the commercial motion: `AssessmentReport`, `Engagement`, `AuditLog`, `WebhookEvent`.
- Define a **placeholder auth/session contract** (`getCurrentSession`, `getCurrentUser`, `getCurrentOrganization`) that pages and API routes consume today; real auth provider lands in v0.3.
- Produce a **typed data-access layer** (`lib/data/*`) that replaces direct `lib/mock/*` imports across pages and API routes.
- Enforce **canonical response envelopes** (`{ ok, data }` / `{ ok, error: { code, message, details? } }`) end-to-end.
- Add **Zod validation schemas** for every inbound API payload + every form contract.
- Add a **deterministic seed** that produces the same demo data the mock fixtures produce, so the dashboards render identically against an empty DB.
- Ship **Vitest unit + integration tests** that cover the data-access layer and validation; wire into the existing `validate` CI workflow.
- Keep the entire surface **provider-agnostic** — no Twilio / Retell / Vapi / Bland / Stripe / GHL / HubSpot / Resend SDK calls in v0.2.

### Non-goals (explicitly deferred)

- **No UI implementation.** [`DESIGN.md`](../DESIGN.md) is the bible for what data the page must be able to display, but v0.2 only swaps the **data source** behind those pages. Visual rebuild against the design tokens is its own milestone (v0.2 closeout / v0.3).
- **No live provider integrations.** No new SDKs in `package.json` beyond `@prisma/client`, `prisma`, `zod`, and a test runner. No real webhook signature validation yet (markers stay).
- **No Stripe billing, no pricing engine, no outcome-fee ledger, no invoice logic.** Those are explicitly v0.5 per [`docs/pricing-and-onboarding.md`](./pricing-and-onboarding.md). The `Engagement` table only **records** the chosen tier and outcome-fee structure as configuration; it does not compute or invoice anything.
- **No Knowledge Layer.** v0.4+ per [`docs/research-report.md`](./research-report.md#future-knowledge-layer--agent-grounding-layer).
- **No `Organization` → `Account` rename.** Planning-spec Goal 3 calls for it; this implementation spec **defers the rename** to v0.3 to keep v0.2 a non-destructive additive change. The tenant root stays `Organization` in v0.2 code; the rename is an [open question](#11-open-questions).
- **No `Booking` → `Appointment` rename.** Same rationale.
- **No production deployment.** No Vercel deploy, no CI deploy job, no env secrets added.
- **No Firebase. No Codex automations. No vector / RAG infrastructure.**

## 2. Schema delta

The v0.1 schema lives in [`prisma/schema.prisma`](../prisma/schema.prisma) with 11 models. v0.2 **adds 4 models** and **adds nothing else**. Every existing model and enum stays unchanged.

### New models (v0.2)

```prisma
// Phase 1 deliverable from pricing-and-onboarding.md.
// One report per business that runs the Readiness & Revenue Leak Assessment.
// Used by: v0.2 admin assessment list, v0.4 client-facing readiness UI, v0.5 outcome-fee baseline.
model AssessmentReport {
  id                       String                 @id @default(cuid())
  organization_id          String                 // FK to Organization (tenant scope)
  status                   AssessmentStatus       @default(draft)

  // Inputs (assessment evaluates these per pricing-and-onboarding.md §What it evaluates)
  inputs_json              Json                   // missed-call volume, after-hours demand, avg job value, close rate, response time, lead sources, CRM readiness, booking workflow, quote workflow, follow-up process, calendar readiness, escalation process, compliance risk

  // Outputs (deliverables per pricing-and-onboarding.md §Assessment deliverables)
  readiness_score          Int?                   // 0-100; null until computed
  revenue_leak_estimate    Int?                   // cents per month
  fit_diagnosis            FitDiagnosis?          // ai_fit | borderline | no_fit
  current_workflow_map     Json?                  // structured map of current process
  recommended_workflow_map Json?                  // structured map of recommended process
  implementation_scope     String?                // free-form
  projected_roi_multiple   Float?                 // recovered revenue ÷ platform cost

  // Pricing proposal (bridge into Phase 2 — recorded for context, not enforced)
  proposed_tier            EngagementTier?        // recovery_core | recovery_pro | recovery_performance
  proposed_setup_cents     Int?
  proposed_monthly_cents   Int?
  proposed_outcome_terms   Json?                  // outcome-fee config draft

  // Lifecycle
  delivered_at             DateTime?              // when packet was sent to client
  signed_at                DateTime?              // when client signed Pricing Proposal (transitions to Engagement)
  created_at               DateTime               @default(now())
  updated_at               DateTime               @updatedAt

  @@index([organization_id])
  @@index([status])
  @@index([created_at])
}

enum AssessmentStatus {
  draft        // operator filling out
  in_review    // packet drafted, awaiting AJ Digital QA
  delivered    // sent to client
  signed       // client signed Pricing Proposal → Engagement created
  declined     // client declined; no engagement
  expired      // 14-30d credit window passed without signature
}

enum FitDiagnosis {
  ai_fit       // qualifies under all gates
  borderline   // some gates marginal, requires operator judgement
  no_fit       // explicit no-fit, no implementation
}

// Phase 2 record from pricing-and-onboarding.md.
// One Engagement per signed Pricing Proposal. Records the chosen tier + terms.
// v0.2: configuration only (no money math).
// v0.5: drives Stripe / outcome-fee invoicing.
model Engagement {
  id                       String                 @id @default(cuid())
  organization_id          String                 // FK to Organization (tenant)
  assessment_report_id     String                 @unique  // FK to AssessmentReport that produced it

  tier                     EngagementTier
  status                   EngagementStatus       @default(active)

  // Pricing snapshot at signing (cents). Read-only after signing; do not recompute.
  setup_fee_cents          Int
  monthly_fee_cents        Int
  outcome_fee_kind         OutcomeFeeKind?        // exactly one or none
  outcome_fee_terms_json   Json?                  // per-engagement structure (rate, threshold, baseline)

  // Usage policy from pricing-and-onboarding.md §Usage and pass-through
  usage_model              UsageModel             // bundled_with_cap | passthrough_with_margin
  included_voice_minutes   Int?                   // applicable when usage_model = bundled_with_cap
  passthrough_margin_pct   Int?                   // applicable when usage_model = passthrough_with_margin

  // Founding Client Pilot flags
  is_founding_pilot        Boolean                @default(false)
  pilot_ends_at            DateTime?              // 90-day window when pilot

  signed_at                DateTime               // bridge from AssessmentReport.signed_at
  started_at               DateTime?              // implementation kickoff
  ended_at                 DateTime?              // engagement terminated
  created_at               DateTime               @default(now())
  updated_at               DateTime               @updatedAt

  @@index([organization_id])
  @@index([status])
  @@index([signed_at])
}

enum EngagementTier {
  recovery_core
  recovery_pro
  recovery_performance
}

enum EngagementStatus {
  active
  paused
  cancelled
  completed
}

enum OutcomeFeeKind {
  per_qualified_appointment   // $25-150
  per_verified_recovered_lead // $25-100
  pct_recovered_revenue       // 3-8%
  threshold_bonus             // $500-2000 above N booked jobs
}

enum UsageModel {
  bundled_with_cap
  passthrough_with_margin
}

// Admin action audit log per v0.2-planning-spec Goal 7.
// Append-only. Tenant-scoped where applicable; null tenant for AJ-internal events.
// Used by: v0.2 admin Activity feed, v0.3 break-glass tracking, future compliance exports.
model AuditLog {
  id              String     @id @default(cuid())
  organization_id String?    // null for cross-tenant AJ-internal events
  actor_user_id   String?    // null for system events
  actor_type      ActorType                       // user | system | webhook
  action          String                          // free-form verb e.g. "lead.qualified", "engagement.signed"
  target_type     String?                         // e.g. "Lead", "Engagement", "AssessmentReport"
  target_id       String?
  metadata_json   Json?                           // before/after diff, request id, etc.
  ip_address      String?
  user_agent      String?
  created_at      DateTime   @default(now())

  @@index([organization_id])
  @@index([actor_user_id])
  @@index([action])
  @@index([created_at])
}

enum ActorType {
  user
  system
  webhook
}

// Webhook event ledger foundation per v0.2-planning-spec Goal 4 + 8.
// Append-only. v0.2: writes only on test/seed paths; v0.3: real provider traffic lands here first.
// Dedupe key: (provider, provider_event_id).
model WebhookEvent {
  id                String          @id @default(cuid())
  organization_id   String?         // resolved post-ingest where possible; null until matched
  provider          String                          // "twilio" | "retell" | "vapi" | "bland" | "stripe" | "ghl" | "n8n"
  provider_event_id String                          // Twilio MessageSid/CallSid, Retell call_id, Stripe event.id, etc.
  event_type        String                          // provider-defined event name
  raw_body          String                          // exact request body, preserved for replay + signature recheck
  signature_header  String?                         // X-Twilio-Signature, x-retell-signature, Stripe-Signature, X-GHL-Signature
  signature_valid   Boolean         @default(false) // false until verified; v0.2 stays false (no real verification yet)
  dedupe_hash       String                          // hash(provider + provider_event_id)
  received_at       DateTime        @default(now())
  processed_at      DateTime?
  process_status    WebhookProcessStatus @default(received)
  process_error     String?

  @@unique([dedupe_hash])
  @@index([organization_id])
  @@index([provider])
  @@index([received_at])
  @@index([process_status])
}

enum WebhookProcessStatus {
  received       // landed, awaiting processing
  processed      // applied to business state
  rejected       // signature invalid or schema invalid
  duplicate      // dedupe hash already seen
  error          // processing failed; see process_error
}
```

### Existing models — unchanged in v0.2

`Organization`, `User`, `Contact`, `Call`, `LeadEvent`, `LeadQualification`, `Booking`, `QuoteRequest`, `Automation`, `Notification`, `RevenueMetrics`. All 19 v0.1 enums unchanged.

### Indexes + constraints summary

- Every per-tenant table carries `organization_id` with an index (already true in v0.1; new tables follow the same rule).
- `AssessmentReport.id` is the FK target for `Engagement.assessment_report_id` (`@unique` enforces 1:1).
- `Engagement.organization_id` does **not** enforce one-engagement-per-tenant; a tenant may have a closed Engagement and a new active one. Application logic ensures only one `status = active` per tenant.
- `WebhookEvent.dedupe_hash` is `@unique` — replays are no-ops.
- `AuditLog` carries no FK constraints (kept loose so deletes elsewhere don't cascade-delete audit history).

### Money fields

Always integer cents (`setup_fee_cents`, `monthly_fee_cents`, `revenue_leak_estimate`, `proposed_setup_cents`, `proposed_monthly_cents`). Same convention as v0.1.

### JSON vs scalar

JSON blobs are used **only** for shapes that are likely to evolve quickly during pilot (assessment inputs, workflow maps, outcome-fee terms, audit metadata, webhook raw body). All numeric scoring fields and pricing fields are scalar so the DB can index and aggregate them.

## 3. Auth + session boundaries

### v0.2 posture: placeholder session, no auth provider install

v0.2 does **not** install Clerk, Auth.js, Supabase Auth, or any other paid/third-party auth library. The session contract below is the public surface that pages and API routes call **today**, against a deterministic dev-mode session. v0.3 swaps the implementation behind the same contract.

### Session contract (`lib/auth/session.ts`)

```ts
// All functions are server-only. Throws on client import.
export async function getCurrentSession(): Promise<Session | null>;
export async function getCurrentUser(): Promise<SessionUser | null>;
export async function getCurrentOrganization(): Promise<Organization | null>;
export async function requireRole(role: UserRole | UserRole[]): Promise<Session>; // throws 403 on mismatch
export async function requireTenantScope(organizationId: string): Promise<void>; // throws 403 on cross-tenant access

interface Session {
  user: SessionUser;
  organization: { id: string; slug: string; name: string } | null; // null for cross-tenant aj_admin
  expires_at: string; // ISO8601
}

interface SessionUser {
  id: string;
  email: string;
  name: string;
  role: UserRole; // from existing types/user.ts: aj_admin | operator | client_admin | client_viewer
}
```

### v0.2 implementation: deterministic dev-mode

`getCurrentSession()` returns a fixed session derived from an env switch:

| Env var | Resolved session |
|---|---|
| `RESPONSEOS_DEV_SESSION=aj_admin` | `{ user: { role: "aj_admin" }, organization: null }` (cross-tenant) |
| `RESPONSEOS_DEV_SESSION=operator` | `{ user: { role: "operator" }, organization: null }` |
| `RESPONSEOS_DEV_SESSION=client_admin@org_mock_1` | `{ user: { role: "client_admin" }, organization: { id: "org_mock_1", … } }` |
| unset (default) | `{ user: { role: "aj_admin" }, organization: null }` |

This lets the team test client-portal pages by switching the env var, without standing up real auth.

### Tenant scoping rules (enforced by `requireTenantScope`)

- `aj_admin`: bypasses scope check — full cross-tenant read/write.
- `operator`: bypasses scope check for reads; writes are logged in `AuditLog`.
- `client_admin` / `client_viewer`: must match `session.organization.id === resource.organization_id`. Mismatch → `403 { code: "tenant_scope_denied" }`.

### Role hierarchy (per [`DESIGN.md` §6](../DESIGN.md#6-admin-experience) + [§7](../DESIGN.md#7-client-portal-experience))

```
aj_admin (super-admin, AJ Digital staff)
  └─ operator (AJ Digital staff, scoped operations)
       └─ client_admin (tenant owner — sees all tenant data, can write)
            └─ client_viewer (tenant team member — read-only)
```

Cross-role access matrix lives inline in `lib/auth/session.ts` as a typed table; not duplicated here.

### Login surfaces (planned, not built in v0.2)

- `/admin/login` — AJ Digital staff (`aj_admin`, `operator`)
- `/client/login` — tenant users (`client_admin`, `client_viewer`)
- Password reset flow: contract only, no implementation. Reset-token table is a v0.3 add (or is delegated to whichever auth provider lands).

### Why no auth library in v0.2

Auth provider choice is an open question (see [§11](#11-open-questions)). Picking Clerk vs Auth.js vs custom-DB-backed has cost, vendor-lock-in, and BAA implications that the user wants to decide explicitly. Shipping v0.2 with a placeholder keeps that decision open without blocking the rest of the data foundation.

## 4. Data access modules

### Layout

All data-access modules are **server-only** (`import "server-only"` at the top of each file). They consume the shared `lib/db/client.ts` Prisma singleton and fall back to `lib/mock/*` fixtures when `db === null`.

```
lib/
  db/
    client.ts                  Prisma singleton + missing-DATABASE_URL fallback to null
  data/
    organizations.ts           Tenant CRUD (operator only)
    users.ts                   User CRUD; role assignment (aj_admin only for cross-tenant)
    contacts.ts                Tenant-scoped contact CRUD
    calls.ts                   Tenant-scoped call reads (writes via webhook ingest in v0.3)
    leads.ts                   LeadEvent + LeadQualification reads + status transitions
    bookings.ts                Tenant-scoped booking reads
    quotes.ts                  Tenant-scoped quote-request reads
    assessments.ts             AssessmentReport CRUD; transitions to Engagement
    engagements.ts             Engagement CRUD; tier + outcome-fee config (no money math)
    auditLogs.ts               Append-only logger; admin action stream reader
    webhookEvents.ts           Append-only ingest; dedupe-aware writer; reader for admin diagnostics
    revenueMetrics.ts          Period aggregator + reader
  auth/
    session.ts                 (per §3)
```

### Public function shape

Every accessor returns the canonical envelope per [`docs/api-spec.md`](./api-spec.md):

```ts
type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string; details?: Record<string, unknown> } };
```

Examples:

```ts
// lib/data/leads.ts
export async function listLeads(params: {
  organizationId?: string;          // optional only for aj_admin / operator
  status?: LeadEventStatus;
  limit?: number;
  cursor?: string;
}): Promise<Result<{ leads: LeadEvent[]; nextCursor: string | null }>>;

export async function getLeadById(id: string): Promise<Result<LeadEvent>>;

export async function transitionLeadStatus(id: string, to: LeadEventStatus, notes?: string): Promise<Result<LeadEvent>>;
```

### Tenant scoping

Every accessor calls `getCurrentSession()` first. For `client_admin` / `client_viewer`, it derives `organizationId` from the session and ignores any caller-supplied `organizationId` parameter. For `aj_admin` / `operator`, the parameter is honored.

### No live provider calls

Webhooks land in `WebhookEvent` and stop there in v0.2. No downstream Twilio / Retell / Stripe / GHL adapter calls. The processing step (`process_status: received → processed`) is a v0.3 wiring task.

### Mock fallback

When `DATABASE_URL` is unset, every accessor short-circuits to the matching `lib/mock/*` fixture and returns the same `Result<T>` envelope. The page-level rendering is identical. CI builds without a database remain green.

## 5. Seed strategy

### File: `prisma/seed.ts`

Idempotent — running twice produces the same final state. Uses `prisma.upsert` for every record. Run via `npx prisma db seed` (script entry added to `package.json` in the implementation PR, not this spec).

### Seed contents (minimum viable)

| Entity | Count | Notes |
|---|---|---|
| User (`aj_admin`) | 1 | `aj@responseos.example` — super-admin |
| Organization | 1 | `org_demo_acme` — "Acme HVAC" — slug `acme-hvac` |
| User (`client_admin`) | 1 | `owner@acme.example` — owner |
| User (`client_viewer`) | 1 | `manager@acme.example` — office manager |
| AssessmentReport | 1 | status `signed`, fit `ai_fit`, with synthetic inputs + recommended workflow map |
| Engagement | 1 | tier `recovery_pro`, status `active`, founding pilot true, signed 14 days ago |
| Contact | 5 | Synthetic names; phone numbers in `+1555…` test range only |
| Call | 3 | Mix of `answered` (Retell), `missed` (Twilio), `voicemail` (Twilio) |
| LeadEvent | 5 | Mixed states: `new`, `qualified`, `booked`, `quoted`, `archived` |
| LeadQualification | 3 | Attached to qualified + booked + quoted leads |
| Booking | 2 | One `confirmed`, one `scheduled` |
| QuoteRequest | 1 | status `sent` |
| RevenueMetrics | 1 | Current month: matches existing mock fixture values exactly so dashboards render identically |
| AuditLog | ~6 | One per non-system mutation in the seed (creates `engagement.signed`, `lead.qualified`, etc.) |
| WebhookEvent | 0 | Seeded empty; v0.3 ingest path fills this |

### PII rule

Phone numbers use the `+1555…` reserved test range. Email addresses use `.example` TLDs. No real names, no real addresses. The seed is safe to run in any environment.

### Determinism

Every seeded ID uses the existing `org_mock_1` / `contact_mock_*` / `lead_mock_*` IDs from `lib/mock/*`. This means the database-backed dashboards display **the same numbers and labels** as today's mock fixtures, satisfying the "no visual regression" acceptance criterion.

## 6. Validation rules

### Library

`zod` (single new runtime dep). Schemas live under `lib/validation/`.

### Layout

```
lib/
  validation/
    common.ts                 cuid, ISO date, E.164 phone, cents, organization_id helpers
    organization.ts           CreateOrganizationInput, UpdateOrganizationInput
    user.ts                   CreateUserInput, UpdateRoleInput
    lead.ts                   TransitionLeadStatusInput, QualifyLeadInput (matches existing scoring helper)
    assessment.ts             CreateAssessmentInput, SubmitAssessmentInput, SignAssessmentInput
    engagement.ts             CreateEngagementInput (validates tier ↔ outcome_fee_kind ↔ usage_model combinations)
    webhook.ts                Per-provider raw payload schemas: TwilioVoiceWebhookSchema, RetellCallEndedSchema, StripeEventSchema, GHLContactWebhookSchema
    api.ts                    Re-exports request/response schemas per route
```

### Brand language enforcement

All user-facing string enums and labels validated through Zod use the canonical labels from [`DESIGN.md` §11](../DESIGN.md#11-ux-writing-rules):

```ts
export const LeadStatusLabel = z.enum([
  "Recovered", "Booked", "In Progress", "Needs Review", "Escalated", "Archived"
]);
// Maps to internal LeadEventStatus enum at the data-access boundary.
```

Banned phrases (from DESIGN.md §11 avoid-list) are caught by an ESLint custom rule pre-commit; not Zod's job.

### Server-side recalculation

Every score/dollar field accepted from a client form is **recomputed server-side** before write:

- `qualification_score`: recomputed from `LeadQualificationInput` via existing `lib/scoring/leadQualificationScore.ts`. Client-supplied score ignored.
- `revenue_leak_estimate` on `AssessmentReport`: recomputed from `inputs_json` via a new `lib/revenue/calculateRevenueLeak.ts` helper.
- `setup_fee_cents` / `monthly_fee_cents` on `Engagement`: validated against the tier ranges in `pricing-and-onboarding.md` (Core: 250000–400000 setup, 75000–125000 monthly; Pro: 500000–850000 setup, 150000–250000 monthly; Performance: 850000+ setup, 250000+ monthly). Out-of-range fees fail validation with `code: "validation_failed", details: { field, allowed_range }`.

### Error envelope

Validation failures always return:

```json
{
  "ok": false,
  "error": {
    "code": "validation_failed",
    "message": "Request body failed schema validation.",
    "details": { "fields": [ { "path": "tier", "issue": "required" } ] }
  }
}
```

## 7. Tests

### Frameworks

- **Vitest** for unit + integration (single test runner).
- **Playwright** is a v0.3 add (UI hasn't been rebuilt yet against DESIGN.md tokens; e2e against the v0.1 scaffold isn't load-bearing).
- No mocking library beyond Vitest's built-in `vi.mock`.

### Coverage by level

| Level | Scope | Target |
|---|---|---|
| Unit | `lib/data/*` accessors with Prisma mocked, `lib/validation/*` Zod schemas, `lib/scoring/*` and `lib/revenue/*` helpers | 80%+ line coverage on these dirs |
| Integration | Each accessor against a real Postgres test database (Docker compose locally; service container in CI). Verifies tenant scoping, audit-log emission, and seed determinism | Every public accessor function exercised at least once |
| Smoke | `npm run build` from a clean checkout with `DATABASE_URL` unset, then again with `DATABASE_URL` set to the seeded test DB. Both succeed | Run in CI per PR |

### Test data factories

`tests/factories/*.ts` exports typed factory functions (`makeOrganization()`, `makeUser({ role })`, `makeAssessmentReport({ status })`, etc.). Each factory uses deterministic IDs (`org_test_001`, `lead_test_001`) so snapshots are stable.

### Tenant scoping tests

Mandatory. Every accessor that takes `organizationId` has at least three tests:

1. `aj_admin` reads across tenants — passes.
2. `client_admin` of org A reads org A — passes.
3. `client_admin` of org A reads org B — fails with `code: "tenant_scope_denied"`.

### CI integration

The existing `.github/workflows/ci.yml` `validate` job runs `npm run lint`, `npm run typecheck`, `npm run build`. v0.2 adds `npm test` after `npm run typecheck`. A separate matrix entry runs `npm run test:integration` against a Postgres service container.

`ci.yml` changes are scoped to adding two lines (`npm test` step + Postgres service); no deploy job, no environment secrets, no new workflow files.

## 8. Risks + rollback

### Schema migration risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `prisma migrate deploy` fails on first run because schema drifts from existing DB state | Low (no production DB exists) | Build only | Seed against a fresh DB in CI; no prod DB to drift from |
| New unique constraint on `WebhookEvent.dedupe_hash` collides with hand-seeded duplicates | Low | Migration aborts | Seed scripts use `prisma.webhookEvent.upsert` with the dedupe hash as the where clause |
| Adding `Engagement.assessment_report_id` `@unique` blocks future use cases (e.g. multi-engagement per assessment) | Medium | Future migration | Keep `@unique` for v0.2; relax to `@@index` if v0.5 commercial work needs it. Migration is non-destructive |
| `AuditLog.organization_id` nullable column slows queries | Low | Read latency | Add the existing index; revisit if Activity feed slows past 100ms p95 |

### Data-loss scenarios

**None expected.** v0.2 only adds tables and columns. No drops, no renames, no type changes on existing columns. The `Organization` → `Account` rename and `Booking` → `Appointment` rename are **explicitly deferred** to keep the migration additive.

### Auth / session leakage

Cross-tenant data leakage is the highest-impact risk if the placeholder session is misused. Mitigations:

- `requireTenantScope()` is the **only** gate; bypassing it requires deleting code, not slipping past a check.
- Every `lib/data/*` accessor is unit-tested with the three-case tenant matrix above.
- The `RESPONSEOS_DEV_SESSION` env var is documented as **dev-mode only**; production code must reject it (the env-resolution function throws if `NODE_ENV === "production"` and the var is set).
- Real auth in v0.3 replaces the placeholder behind the same contract.

### Connection pooling under load

If the team picks Neon as the Postgres host, the Prisma client must use the pooled connection string (`DATABASE_URL`) at runtime and the direct connection (`DIRECT_URL`) only for migrations. The schema already declares both. The `lib/db/client.ts` singleton enforces pooled-only at runtime.

### Rollback plan

- v0.2 lands in 3–4 sub-PRs (see [§9](#9-implementation-phases)).
- Each sub-PR is independently revertable via `git revert <sha>` because none of them deletes data.
- The Prisma migrations are append-only — a revert leaves the new tables in the DB but unused; a follow-up migration can drop them if needed.
- The mock-fallback path means reverting any sub-PR back to mock-mode is a `DATABASE_URL=` (empty) restart away.

## 11. Open questions

These need explicit user decisions before implementation begins. Surfacing them here so they're answered once and for all before sub-PRs start.

### Q1 — Database host

- **Option A:** Neon (planning-spec leans Supabase/Postgres-compatible; Neon is widely used at AJ Digital from FPLP / audiojones work).
- **Option B:** Supabase Postgres (planning-spec text says "Supabase / Postgres-backed").
- **Option C:** Local Postgres only for v0.2; pick a host in v0.3.
- **Default if unanswered:** Option C — local Postgres for v0.2 dev + CI; defer host pick.

### Q2 — Auth provider for v0.3

The v0.2 implementation uses a placeholder session ([§3](#3-auth--session-boundaries)). v0.3 swaps in a real provider.

- **Option A:** Auth.js (`next-auth`) with Prisma adapter, db-backed sessions. Open-source, no SaaS lock-in. Matches FPLP convention.
- **Option B:** Clerk (planning-spec line 63 mentions Clerk-backed). Faster to ship, hosted UI, has org-aware primitives. Costs money per MAU.
- **Option C:** Custom DB-backed sessions + bcrypt + JWT. Most control, most work.
- **Default if unanswered:** Option A — Auth.js.

### Q3 — `Organization` → `Account` rename

Planning-spec Goal 3 calls for it. This implementation spec defers it to v0.3 to keep v0.2 additive.

- **Option A:** Defer to v0.3 (current default in this spec).
- **Option B:** Do the rename in Phase A as a Prisma migration; update all 11 v0.1 model `organization_id` references and the data-access layer.
- **Default if unanswered:** Option A — defer.

### Q4 — Should v0.2 add a real `Session` table?

- **Option A:** No — keep the placeholder session in `lib/auth/session.ts` (current default). Real session table arrives in v0.3 with the auth provider.
- **Option B:** Yes — add `Session` table now, even though v0.2 doesn't write to it, so the schema is forward-compatible.
- **Default if unanswered:** Option A — placeholder only.

### Q5 — `AssessmentReport.inputs_json` shape — strict or free-form?

The assessment evaluates 14 inputs per [`pricing-and-onboarding.md`](./pricing-and-onboarding.md#what-the-assessment-evaluates). Two ways to model:

- **Option A:** `Json` field with a Zod schema enforcing the 14 fields server-side (current default; flexible).
- **Option B:** Promote the 14 inputs to scalar columns on `AssessmentReport`. More queryable, less flexible.
- **Default if unanswered:** Option A — JSON + Zod.

### Q6 — `AuditLog` retention policy

How long does an audit log row live?

- **Option A:** Forever — never delete (current default; safest for compliance).
- **Option B:** 2 years, then archive to cold storage.
- **Option C:** 1 year, hard delete.
- **Default if unanswered:** Option A — forever.

### Q7 — Phase A vs B vs C ordering

Current default ([§9](#9-implementation-phases)): A → B → C (sequential, each depends on the prior). Alternative: split B into B1 (auth contract) + B2 (data accessors) so the auth contract lands earlier and Phase C can proceed in parallel with B2.

- **Option A:** A → B → C → D sequential (current default).
- **Option B:** A → B1 (auth) → (B2 data + C consumers in parallel) → D.
- **Default if unanswered:** Option A — sequential, simpler.

### Q8 — Fixture parity threshold

Acceptance criterion 6 says "every page renders the same numbers as today against the seeded DB." Strict character-for-character, or "same metrics within rounding"?

- **Option A:** Strict — seeded DB produces byte-identical render output for every dashboard page.
- **Option B:** Loose — same metric values within ±$1 rounding tolerance.
- **Default if unanswered:** Option A — strict (the seed is deterministic; this is the easier guarantee).
