## Recovery action

Authenticated operators may POST /api/admin/call-capture/[id]/withdrawal-recovery with receiptId, expectedAccountId, expectedProviderCallId and generation, plus optional original disclosureRef/evidenceRef/jurisdictionBasis/withdrawalSourceTime. Identity assertions are compared to the stored capture and existing receipt. Missing receipt refuses recovery and creates none; mismatch/stale generation refuses before drain. Legacy receipts with matching identity can drain but missing original key/hash requires evidence review.

The event key is always read from the receipt. A supplied eventKey is rejected by the strict request schema, including inside original. The new action never persists a receipt or rewrites first actor/time/identity/history. It attempts bounded idempotent drain, then writes withdrawal evidence only when original form inputs match the receipt's request hash. Missing/mismatched inputs return explicit review_required while an otherwise valid drain remains useful. Exact evidence is idempotent; earlier evidence is preserved. Classification of NEW evidence uses the current call state and current supported consent/source-time boundaries at continuation, not reconstructed receipt-time state. The new evidence actor is the continuing authenticated operator; the original receipt actor remains intact. Evidence recorded_at retains existing receipt chronology and is not the later evidence commit time.

The existing receipt/drain/evidence logic is factored only to reuse the database evidence stage. The original consent route still persists receipt, drains, records evidence and attempts AI stop. Its retry behavior and all command retry semantics remain unchanged. The new action has no call to the command executor, provider adapter, generic webhook replay or post-call finalizer. A concurrently running original route may independently send AI stop: no claim of zero provider actions for the entire session is made.

Receipt, drain, evidence, command response and confirmed disconnection remain separate. An interrupted drain returns durable progress when readable; database unavailability remains an error, not proof of completion. A commit followed by lost acknowledgement can be retried through the DB-only action without creating duplicate receipt/evidence or sending a command. Generation is rechecked with a capture row lock during bounded drain and evidence work. No consent, withdrawal or disconnection marker can be reopened by this action.

It is NOT receipt time and is NOT exact commit time. The earlier external withdrawal-ordering design's contrary receipt-time description is corrected here; that design artifact is historical, not current authority. No migration or clock behavior changes.

## Operator labels and read-only End call phases

The existing effect-capable action is labelled “Retry withdrawal (may send AI stop)” after withdrawal/terminal state. The separate action is “Continue database processing (no provider action).” It uses the original form fields and never asks for a new event key. The UI explains current-state classification and the independent original-route caveat.

End call status uses matching call_end_requested audit metadata to classify operator, automatic/system or unknown origin. A matching operator call_end_authorized witness must bind command row/UUID, account, capture, assignment, provider call and generation. Missing/ambiguous origin remains unknown. System/unknown reservations explicitly say they may already have sent. Operator reservations without an authorization witness do not prove unsent and may still progress. An authorization witness proves authorization, not delivery; recorded command response is not disconnection. No terminal-unsent outcome is recorded, no claim is released, no send authority is added and no hangup retry becomes available. The hangup implementation is unchanged.
