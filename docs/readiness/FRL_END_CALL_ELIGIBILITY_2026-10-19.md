## Exact eligibility rule

Within the existing account/capture lock, fresh signature-bound original hangup evidence must match account, provider, event ID/type, call-control/session/leg, capture ID and generation before disconnection is confirmed. An existing same-generation hangup claim is returned idempotently without resending, regardless of command outcome. A claim from any other generation is a veto against a new hangup for the capture. No retry control is offered after a claim. ## Retention and ambiguity

Presentation states are fresh, expired, erased, absent and unverifiable. Only fresh has confirmed=true and event/time evidence. All others return null proof details. Expired/erased categories describe retained metadata candidates, not a verified link to this generation. Erasure deliberately clears provider-call correlation; the console may only report account-level erased/unattributable hangup evidence. Such a candidate blocks new End calls for that account, conservatively including unrelated captures, until an independently authorized resolution exists. No mapping or payload is retained to bypass erasure. A fresh exact hangup can still confirm its own capture. Unattributable or invalid hangup metadata also vetoes dispatch.

The account-level veto is an intentional availability cost. There is no UI override, force retry, expiry-based release or provider lookup. Existing retained lifecycle boundaries and one-shot claims survive loss of original proof; neither is displayed as freshly verified disconnection. If the original row and its association have already been erased/deleted without a lifecycle boundary, exact historical attribution cannot be recovered. Fresh active identity is still mandatory and ambiguity is not resolved by normalized status. This patch does not manufacture historical facts.
