# Webhook fingerprint: additive local candidate

Owner approved local schema authoring/testing and isolated CLI verification on October 18. This supersedes the earlier pending-approval status for those two steps only. No hosted migration, application ingestion binding, key provisioning or activation is included.

Migration `0018_webhook_content_fingerprint` adds a nullable tuple to `WebhookEvent`: lowercase HMAC-SHA-256 `CHAR(64)`, version `SMALLINT` fixed to 1, and nonsecret key ID `VARCHAR(64)` with `[A-Za-z0-9][A-Za-z0-9_.-]{0,63}` syntax. PostgreSQL CHAR padding is removed by the text cast before the exact 64-hex regex; short digests fail. Existing provider/event and dedupe uniqueness is unchanged. No new index, table or historical backfill.

The CHECK requires either all-null or all-present valid fields, a verified-signature marker, finite non-null expiry and no purge marker. The database cannot itself prove signature verification or HMAC correctness: only the synthetic scaffold currently computes the tuple, after Ed25519 verification of exact original bytes and before storing a redacted body. Real ingestion does not populate or consume this tuple.

Binding occurs on initial INSERT only. All UPDATE null-to-populated transitions are forbidden, including legacy, redacted, restored or erased records. Populated tuples and provider/event/dedupe identity cannot change. Their expiry may shorten, never extend or become null. No existing row is assigned new identity from its mutable body.

An existing retention update setting `payload_purged_at` automatically clears the tuple in the same BEFORE trigger. It must use an OLD expiry already elapsed according to database wall time, and a purge timestamp between that expiry and current database time. Same-statement shortening cannot justify early erasure. This keeps old retention writers compatible without an application change. It does not add a scheduler: expired tuples fail recovery immediately, physical erasure still depends on the existing authorized purge operation. No indefinite or infinite expiry is allowed for populated tuples.

After erasure, a privileged legacy writer may still clear the existing purge marker/change the body; that broader behavior is intentionally not changed. It cannot restore the tuple, and identity-required recovery still fails. Database owners can disable triggers or delete/reinsert rows; this is not tamper-proof evidence against a privileged administrator. Restore/backup policy must also honor expiry. Existing purge callers that intentionally use a future simulated timestamp cannot purge a populated tuple ahead of database time.

The local test scaffold uses synthetic keys only, INSERT ON CONFLICT DO NOTHING followed by constant-time digest verification. Concurrent identical events resolve to one binding; conflicting originals fail. Unknown version, unavailable/retired/wrong key, legacy, purged, missing expiry and expired records fail closed. This behavior is tested in the scaffold, **not implemented in production recovery**. Unsupported database versions are rejected by CHECK; the recovery negative uses a hypothetical future row in memory.

Independent review covers the exact SQL, trigger and tests. Existing migration chains plus synthetic upgrade compatibility, restore/schema checks and PG16/17/18 are required before local handoff. Prisma schema diff does not verify trigger semantics; executable transition tests supply that evidence.

Rollback posture: stop any future identity-required ingestion/recovery before rolling application code back. Retain additive columns, CHECK and trigger, retain purge operation, and do not drop or backfill evidence. Old inserts remain all-null/unverifiable; old ordinary updates remain compatible; existing expiry updates clear the tuple. The local rollback test models this posture, not a hosted rollback drill. No down migration is supplied because dropping proof while recovery is enabled is unsafe.

Review key provisioning/rotation/retirement, retention and rollback coordination separately.
