## Primary evidence and proposed mapping

The [streaming-start command](https://developers.telnyx.com/api-reference/call-commands/streaming-start) supports a per-call WebSocket destination, auth token, client state, command ID, codecs and target legs. Proposed settings are inbound_track, PCMU, RTP bidirectional mode, PCMU output, 8000 Hz and self target leg, subject to validating the actual caller leg. Do not stream on answer: issue streaming_start only after disclosure and saved consent. Do not use both_tracks, which can feed assistant output back into its own input. This is a proposal, not an executed command.

The [WebSocket reference](https://developers.telnyx.com/api-reference/websockets/stream-call-media-over-websocket) documents x-telnyx-streaming-auth-token in the upgrade header and connected frame. Treat it as a one-use bearer capability with a stored hash, expiry and atomic consumption, not as a tenant ID. Match the exact configured URL; redact it and the token from proxy/application logs. The supplied .md URL could not be opened by the web tool; the HTML reference was inspected instead.

The [media guide](https://developers.telnyx.com/docs/voice/programmable-voice/media-streaming) specifies Ed25519 upgrade verification over timestamp|exact-stream-url. Its start frame includes call_control_id, call_session_id, client_state, stream_id and media format. Proposed binding is stored account/capture/generation/assignment/call-leg -> signed command target -> unique authenticated stream token -> checked start-frame call/session/client_state -> one stream_id -> server-created xAI socket/session. The example does not include call_leg_id: retain that leg from previously authenticated Telnyx capture evidence; never invent or derive it from caller From/To. Verify signed streaming.started evidence as available, reject missing/ambiguous identity and do not admit media before the complete binding. Existing WebhookEvent verification is for timestamp|raw-body, so upgrade verification needs its own implementation.

The [xAI voice guide](https://docs.x.ai/developers/model-capabilities/audio/speech-to-speech) supports a versioned model and audio/pcmu at 8 kHz. Proposed bridge uses raw G.711 payloads in JSON/base64 frames, without WAV/RTP headers. Repacketize and pace short bounded chunks; inspect actual negotiated codec, sample rate and mono channel count, reject mismatch rather than silently transcode. Proposed initial frame size is 20 ms/160 PCMU bytes; bounded reorder and output queues require explicit tests. The bridge must not connect xAI, buffer pre-consent audio or forward any bytes until consent/identity checks pass. Tools and resumption remain off. The supplied voice-agent URL redirects to this guide.

Late work: on withdrawal/control loss, atomically close admission, revoke the stream capability, discard local queues, request carrier termination, attempt queue-clear/cancel/socket cleanup as best effort, and ignore every late xAI audio/text/tool result using the original tuple and generation. The media guide documents clear/mark behavior; a returned mark may also mean a queue was cleared, not that audio played. Socket closure is not proof of remote cancellation, billing cessation or erased content. Real queue/pacing/interruption behavior remains qualification work.

The [Telnyx hangup command](https://developers.telnyx.com/api-reference/call-commands/hangup-call) targets the retained call_control_id and expects call.hangup. The existing authenticated exact-call webhook evidence and durable disconnection marker can remain the carrier authority after fresh regression testing. streaming.stopped, a WebSocket stop, HTTP200 and xAI socket closure are not carrier disconnection proof. Independently observed caller termination is still required. Direct SIP instead needs an additional xAI SIP call correlation and terminal contract that the inspected [SIP guide](https://docs.x.ai/developers/model-capabilities/audio/speech-to-speech/sip) has not established for our original Telnyx capture.

## Approved local media bridge successor

Owner selected the Telnyx-controlled media bridge for local implementation after this comparison. SIP expansion stops. `lib/grok/mediaContract.ts` verifies Ed25519 over timestamp plus the exact trusted WSS URL, validates the one-use token and mono PCMU/8000 start tuple, and constructs the post-consent streaming command. `service.ts` atomically consumes the existing correlation capability into an immutable stream receipt and worker token; realtime identity is a separate immutable receipt, never a SIP hangup ID. No migration bytes were changed for this successor.

`lib/grok/mediaBridge.ts` is the transport-independent bridge runtime with injected socket ports. It pins the realtime URL, waits for a strict configuration acknowledgement (model, PCMU, JSON transport, VAD, no tools, no resumption), persists identity, reorders up to five 20ms frames, bounds output to one second, paces 160-byte frames, and limits unacknowledged playback marks. Missing chunks, stale authority, unknown protocol events, overflow, network closure, or faults close admission and request the original carrier-call termination. Pre-configuration media is discarded. Speech-start fences the old response and clears playback; marks and socket closure never prove termination. A watchdog remains a separate process. Current one-second heartbeat checks and three-second local freshness bound require hosted qualification and do not guarantee immediate distributed withdrawal.

The [official realtime reference](https://docs.x.ai/developers/rest-api-reference/inference/voice) supplies session acknowledgement, speech-start, response identity, cancellation and audio event contracts. VAD handles server interruption; the bridge locally fences old output and does not interpret automatic cancellation as remote termination evidence. Strict acknowledgement and 20ms packet assumptions intentionally fail closed if actual provider traffic differs; they require qualification before admission.

This is local application implementation and synthetic socket qualification. Production network listeners, credential-bearing socket construction, independent hosting, account retention and live media behavior remain unqualified. `assertGrokQualified()` still always rejects. No environment flag activates the bridge, and existing SIP verification remains disabled. The socket-port composition is exercised in integration tests, not exposed as a public route. This is not a completed hosted demo or a matching deployable control pair. Final candidate results are external evidence; earlier 40d results do not qualify later changes.
